# 求职进度与保存规则

网页端与 Android 共用 `client/admin/progress.js`。没有修改数据库表结构，也没有自动修正历史记录。

## 审核与求职结果

- `pending`：邮件待审核；不参与主表当前进度计算。
- `ignored`：忽略记录，可恢复；不参与主表当前进度计算。
- `scheduled`：待处理、待投递或待参加。
- `awaiting_result`：已提交或已完成，等待结果；不等于已通过。
- `passed`：明确通过。
- `failed`：本轮未通过或终止。

单条、批量审核共用保守规则：只有环节名称明确表达完成或结果时才采用对应状态。仅有时间、邀请或笼统的环节名称，均进入待处理。AI 提取仍需人工核对，可在编辑窗口修正。新环节不会自动修改前序环节状态。HR 面试不会作为录用沟通；Offer 沟通阶段不直接计入“已录用”指标。

主表进度取 seq 最大的已确认环节。编辑历史环节不覆盖最新快照。撤销当前环节只忽略该环节，上一环节保持原状态；不虚构“网申已提交”或“等待结果”。

## 保存失败与冲突

网页、Android 写入错误均中止并提示。环节与主表分步写入时：主表失败尝试恢复本次环节修改；恢复失败明确要求刷新核对。用 updated_at 条件避免覆盖已变化的记录。批量操作按条执行，发生错误时报告已完成数量，不宣称全部成功。

手动新增先保存待审环节，再确认进度。确认失败保留待审记录，提示用户核对，不应重复点击新增。Android 删除改为可恢复的忽略。

这些是客户端校验与补偿，不是数据库事务。网络响应丢失、补偿失败、旧版客户端写入或多端并发创建仍需要核对；若要数据库级强一致性，应另行部署事务 RPC、唯一约束与权限规则。此次未部署数据库迁移或访问真实业务数据。

## 岗位匹配与邮件重试

自动匹配使用公司、岗位、已提供的部门信息，并允许 active/offered 投递接收新通知。手动新建投递必须填写岗位名称，匹配比较公司、部门和岗位，不再仅按公司复用。重复候选不任选一条：网页提示指定投递，邮件同步停止并保留书签，待人工核对重复记录后重试。

岗位别名和缺失字段不能可靠自动合并，仍可能形成分开的待审记录，需要人工核对。没有引入模糊合并，也没有尝试自动恢复历史误合并。

邮件按 UID 升序处理，只把书签推进到连续成功处理的最后一封。读取、AI 结果格式或入库失败时停止，下一轮重试；数据库查询失败不再被当成“查无记录”。待审邮件不会覆盖已确认的主表快照。

历史上已跳过的邮件与已被改成 passed 的记录无法从当前状态推断原值。本次不会倒退线上书签或批量改历史状态；需根据原邮件人工确认后补录/修正。
